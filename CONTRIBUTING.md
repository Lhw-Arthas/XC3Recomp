# Contributing to Monado

## Project rules (the "constitution")

Non-negotiable rules. Code comments refer to them as "Constitution art. N". Changing an article needs a changelog
entry with the reason.

### Article I — Zero Nintendo content in the repository
1. The repository holds no code, data, assets, keys, firmware, system fonts or binaries of the game, nor anything
   generated from them (lifted C, tables, translated shaders, caches, captures showing assets).
2. Everything derived lives in `targets/`, `build/`, `generated/`, `cache/`, ignored by git.
3. The packager MUST fail when it finds a derived file (`tools/package_guard.py`, run by CI and by a unit test).
4. Allowed: public SDK API names, addresses, counts and version-check hashes.

### Article II — Your own dump, no keys
1. Only `exefs/` and `romfs/` already extracted from the user's own copy are accepted.
2. The project neither ships nor downloads keys or title keys, and never prints them in logs.
3. The version is checked by build-id; a different version is refused with a clear message.

### Article III — Attribution and licences
1. The base is LASRecomp (MIT, © 2026 Peiikai). Its copyright notice MUST stay in `LICENSE` and `NOTICE.md`.
2. Code from GPL-3.0 projects (ssbu-recomp, B2recomp) is only a design reference; copying their code needs an ADR
   accepting GPL-3.0 for the whole project.
3. Every third-party dependency is listed in `NOTICE.md` with its licence.

### Article IV — Traceability
1. Work is tracked in `docs/dev/tasks.md` (task id, what it covers, "done when…").
2. Each change cites its task. Each requirement has at least one test.

### Article V — Tests before trust
1. Lifter: each instruction class is validated against Unicorn before it is used on the game (differential test).
2. Runtime: each synchronisation primitive, service and format has a unit test without game data.
3. No bug fix is accepted without a test (or a recorded route) that reproduces it before the fix.

### Article VI — Fail loudly
1. An unimplemented SVC, IPC command, HLE function or instruction MUST be able to stop the game in strict mode with a
   report (what, where, guest + host stack). Silently returning 0 is only allowed when audited as "simplified".
2. Every HLE implementation is classified `real` / `simplified` / `stub` in `docs/hle_audit.md` (generated by
   `python tools/hle_audit.py` from `games/xcde/hle_classes.tsv`).

### Article VII — Determinism and observability from day one
1. The runtime can run deterministically (fixed clock, recorded input) and emit a per-frame state hash.
2. Hang watchdog, crash reports with a minidump and a profiler exist.

### Article VIII — Measure, don't promise
1. Every performance, memory or stability figure in a README, PR or release states the machine, build, method and log.
2. A target counts as met only with evidence (`docs/evidence/`, logs, captures without assets).

### Article IX — Common runtime, game apart
1. XCDE-specific code belongs in `games/xcde/` where possible (hooks, patches, options, memory profile).
2. What the runtime learns from XCDE should keep serving XC2, XC3 and XCX DE.

### Article X — Upstream first, simplicity
1. The code starts from LASRecomp; rewriting something needs an ADR explaining why adapting it isn't enough. Every
   edit to an upstream file is marked `[XCDE]` and listed in `docs/UPSTREAM.md`.
2. Generic fixes useful to LASRecomp are offered upstream when reasonable.
3. The simplest solution that meets the requirement wins; extra complexity is justified in the plan.

## How changes are made (the loop the project followed)

1. **Reproduce with a deterministic route.** `scripts/drive_env.sh <route> <frames> [secs] [name]` drives the game
   without a window, with `tests/routes/*.txt` input, and saves captures (`build/<name>_<frame>.png`). Set
   `DRIVE_SAVE=<folder with save_0/>` to start from a save, `DRIVE_EXE=` to test another build.
2. **Write the check before the fix:** a unit test (`tests/unit`), a native test (`tests/native`), or a frame-hash
   comparison (`XCDE_FRAME_HASH=<file>` + `tools/hash_diff.py`).
3. **Diagnose with data, not guesses:** the environment switches listed in `docs/dev/HANDOFF.md` (`XCDE_*`,
   `LARECOMP_*`), the sampling profiler (`XCDE_SAMPLE=<from>:<to>`), the watchdog, RenderDoc.
4. **Fix the cause, not the symptom;** minimal change; mark edits to upstream files with `[XCDE] Txxx`.
5. **Verify by measuring:** the check from step 2 green, `scripts/ci.sh` green, and for rendering changes a
   deterministic route compared frame by frame against the previous build (see "Equivalence" below).
6. **Record it:** the task in `docs/dev/tasks.md`, a `HANDOFF.md` entry for anything the next person must know.
7. **Small commits**, one logical change each. Never commit `build/ cache/ save/ targets/ generated/ crash/ play/`.

### Equivalence (no regressions)
Performance or refactoring changes must not change the picture or the game logic. The method used throughout:
- run `tests/routes/load_walk.txt` deterministically with `XCDE_FRAME_HASH`, before and after;
- compare with `tools/hash_diff.py` (identical prefix length, exact %) and the captures pixel by pixel;
- deterministic runs diverge slightly after ~2,000 frames even on the same build (open issue T124: dithered fades,
  timing). Measure that noise with two runs of the *same* build first, and accept a change only if it stays inside it.

### Testing on many machines
`tools/tour_batch.py` runs tours (`tests/tours/*.txt`: warps, events, battles generated from the game's own tables by
`tools/tour_gen.py`) as many short game runs in parallel; `tools/soak.py` runs a long multi-map session and samples
memory every 30 s. Neither reads anything into the repository: their output goes to a work folder you choose.
